# Python Agent 迁移与眼底诊断工作流 Spec

日期：2026-10-12（Asia/Shanghai）  
状态：需求与架构边界已获用户确认；本文是待实现和验收的规范，不代表实现完成。  
交付方式：迁移 worktree 内的 Markdown 文档。  
适用范围：在已有 FastAPI 业务迁移基础上，将 Agent 迁到 Python，并完成受控眼底诊断工作流。

## Problem Statement

用户希望业务后端、算法能力和 Agent 在 Python 技术栈中协同工作。目前迁移 worktree 已有 FastAPI 业务层，算法层复用 PyTorch，但 Agent 仍依赖 Java 实现。另一个 release 分支已经设计了眼底诊断的多角色工作流，当前 worktree 尚未包含它。

用户需要的是能够从聊天或上传页面发起、持续追踪、按需补充信息、经必要复核后提供解释，并在本人确认后保存正式诊断记录的完整过程。仅保存聊天历史、声明多 Agent 角色、展示工具确认事件或存在 checkpoint 类，均不足以证明这些过程已经可用。

已核查的 release 实现提供了角色职责、图拓扑、工作流状态、任务、复核和恢复设计，但尚不能据静态代码确认生产可执行图注册与后台任务执行闭环完成。Python 迁移必须落实这些执行能力，而不只是翻译类名或提示词。

系统沿用 release 的项目定位：眼科辅助诊断演示与研究系统。工程验收不等同于临床验证；系统内医生权限不代表真实执业资质认证。

## Solution

以 release 的眼底诊断职责与业务语义为基线，用 LangGraph 实现 Python 可执行编排，通过 FastAPI 提供 API 和 SSE。业务层继续使用 SQLAlchemy、MySQL、Redis；图像分类继续复用现有 PyTorch 模型及可靠性推理管线；知识库继续使用 ChromaDB 和现有 embedding 配置。

聊天入口与上传入口共享同一个诊断任务、执行状态、解释结果和复核记录。主流程和条件路由由程序定义，各角色可在受限职责内调用工具，不能自行越过质量门、证据校验、临床复核或用户写入确认。

流程保留图片验证、推理、质量判断、风险判断、证据检索、解释生成与校验、必要的人工作业和发布。聊天负责交互、补充说明和解释，正式诊断记录的保存由独立的用户确认流程控制。

## User Stories

1. 作为普通用户，我希望继续使用现有登录方式，以便迁移后仍能访问自己的会话和诊断记录。
2. 作为普通用户，我希望在聊天中发起眼底图片分析，以便不必切换到另一套独立诊断系统。
3. 作为普通用户，我希望从上传页面发起相同的诊断流程，以便按习惯选择入口。
4. 作为普通用户，我希望同一任务在聊天和诊断页面显示一致的进度与结果，以便理解当前处理状态。
5. 作为普通用户，我希望重复点击或网络重试不会创建重复任务，以便避免重复处理。
6. 作为普通用户，我希望图片不合格时收到明确的重新上传或等待复核提示，以便知道如何继续。
7. 作为普通用户，我希望模型不可用时看到准确的失败状态，以便不会把伪造或未训练模型的输出当成结果。
8. 作为普通用户，我希望等待、执行、复核、完成和失败能被区分，以便判断是否需要操作。
9. 作为普通用户，我希望能够在聊天中补充本次说明，以便系统与复核人员看到更新后的上下文。
10. 作为普通用户，我希望系统提出补充信息请求时能够等待我的回复，以便不会反复处理同一份缺失输入。
11. 作为普通用户，我希望系统解释区分模型评估、参考资料、风险提示和医生复核，以便理解各项内容的来源。
12. 作为普通用户，我希望解释附有可追溯的参考来源，以便核对一般性疾病和随访说明。
13. 作为普通用户，我希望证据不足时系统明确说明限制，以便不会收到无依据的完整解释。
14. 作为普通用户，我希望正式保存前查看本次拟保存的内容，以便确认它与我的意图一致。
15. 作为普通用户，我希望能够拒绝保存，以便分析完成不会自动产生正式诊断记录。
16. 作为普通用户，我希望批准只适用于我实际看到的内容版本，以便修改后的结果不会沿用过期授权。
17. 作为普通用户，我希望重复确认不会重复保存，以便不会生成多份相同记录。
18. 作为普通用户，我希望刷新页面或重新连接后继续查看原任务，以便短暂断网不会丢失进度。
19. 作为普通用户，我希望当前会话能记住已经说过的内容，以便避免每轮重复解释。
20. 作为普通用户，我希望引用历史诊断时明确显示来源，以便不会把历史情况误当成本次情况。
21. 作为普通用户，我希望只能访问自己的会话、任务、确认请求和诊断记录，以便不同用户的数据相互隔离。
22. 作为知识库用户，我希望上传 .doc 和表格型 .docx 后能正常检索有效内容，以便迁移不会丢失原有文档能力。
23. 作为知识库用户，我希望私人资料仍受用户访问范围限制，以便普通问答不会访问其他用户文档。
24. 作为复核医生，我希望分别看到图像质量复核与最终临床复核任务，以便按各自职责作出决策。
25. 作为复核医生，我希望看到本次问题、推理来源、证据和解释快照，以便基于同一版本的信息复核。
26. 作为复核医生，我希望领取与提交复核时校验权限和版本，以便并发操作不会覆盖他人的有效决策。
27. 作为复核医生，我希望复核恢复后复用已完成的推理结果，以便审批不会重复生成或改写 AI 来源事实。
28. 作为管理员，我希望能追踪任务、失败原因和关键操作记录，以便定位流程中断的位置。
29. 作为运维人员，我希望服务重启后任务和待确认操作能够恢复，以便运行状态不只存在于进程内存。
30. 作为运维人员，我希望有明确的启动、健康检查、切流和回退步骤，以便能在真实环境中交付迁移。
31. 作为开发者，我希望保留旧业务 API 的兼容行为，以便新增工作流不会破坏已运行的页面。
32. 作为开发者，我希望能够从 HTTP 与 SSE 验证完整用户过程，以便测试能够发现边界接线问题。
33. 作为开发者，我希望区分模拟测试、真实基础设施验证和真实模型验证，以便完成报告如实反映覆盖范围。
34. 作为项目维护者，我希望旧缺陷、迁移修复和主动改变的契约分别记录，以便比较新旧实现的行为。

## Implementation Decisions

### 1. 基线、模块与运行边界

- 业务语义基线为 release/v1.0.0 的已核查提交 5ac742f0db30ded1c87462211a535012d952e4bb；不能用当前单 Agent 主线代替该工作流基线。
- 将角色职责、条件路由和业务不变量迁到 Python，而非直接合并整个 release 或修改 Java 实现。
- Python 分为 API 与事件、会话与聊天、工作流编排、可靠任务执行、推理适配、证据与解释、人工复核、用户操作确认、持久化与审计等模块。沿用现有业务模块边界，不为每个图节点建立独立微服务。
- 首版包含 Image Quality、Vision、Evidence、Explanation、Human Review 职责；确定性节点可以是普通函数或服务，不强制每个节点都调用 LLM。
- Python 3.11 是现有 CI 基线。新增 LangGraph 与模型客户端依赖须验证兼容并锁定可复现版本；不照搬参考项目的宽泛版本下限。
- Java 继续承接三个会话端点。Python Agent 使用服务端验证的登录用户身份，不能信任模型或浏览器传入的 userId、角色和访问范围。
- Agent 切流、现有业务切流与数据库升级分别记录部署步骤。不得让 Java 与 Nginx 竞争同一监听端口或形成代理回环。

### 2. 术语与状态来源

| 术语 | 本规范中的含义 |
|---|---|
| Session | 当前用户的聊天会话，不等同于登录 session，也不等同于诊断工作流。 |
| Workflow | 一次受控眼底诊断的业务聚合，由聊天或上传入口共同引用。 |
| Job | 可靠调度一个图执行分段的任务，负责租约、重试和恢复，不决定业务路由。 |
| InferenceEnvelope | 绑定工作流、图片与推理版本的不可变推理结果包，由质量与影像节点共享。 |
| Explanation Snapshot | 经过来源与声明校验、具有版本的患者可读解释快照。 |
| Review Task | 医生执行图像质量或最终临床复核的任务。 |
| User Action Approval | 用户对某项具体业务写入及其内容版本的批准或拒绝。 |
| Checkpoint | 图执行的继续执行信息，不能充当第二套业务状态机。 |

- MySQL 是 Workflow、Job、Review Task、解释快照、用户确认和审计的唯一业务事实来源；Redis 仅用于缓存或辅助协调。
- LangGraph 是节点拓扑和条件路由的唯一执行定义。Worker 和数据库状态转换不能再复制一套临床路由逻辑。
- 工作流业务状态沿用 CREATED、QUEUED、RUNNING、WAITING_HUMAN_REVIEW、COMPLETED、COMPLETED_LIMITED、REJECTED、CANCELLED、FAILED 的既有含义。
- 用户写入确认的 pending/approved/rejected/expired 等状态归属于确认实体，不能塞进医生 ReviewDecision，也不能将等待用户保存伪装成 WAITING_HUMAN_REVIEW。
- 需要聊天补充输入时，由交互或图中断信息记录等待原因；不得为此未经版本化决策修改已有临床 WorkflowStatus。
- 图定义、动作版本、结果快照和恢复信息须能识别版本；不兼容版本不得静默恢复旧任务。

### 3. 受控编排与推理

- 流程保留图片验证、推理、质量路由、可选质量复核、预测暴露门、风险初筛、证据检索、来源校验、最终风险判断、解释生成、声明校验、必要临床复核与发布的职责和条件语义。
- 不按名称推断图节点已经接线。交付必须有实际注册的可执行图、启动的任务执行器，以及从创建任务到终态的生产调用链。
- 同一 inference epoch 的质量与影像节点共享一个不可变 InferenceEnvelope。恢复、复核和重复投递不得覆盖已提交的推理结果或重复产生业务推理效果。
- 推理复用现有质量、校准、拒绝与模型来源校验管线。Agent、普通诊断入口与 MCP 适配不能各自维护互相矛盾的推理事实。
- 权重缺失、来源不匹配或推理失败时明确失败或不可用；不得退回未训练模型、默认类别或伪造成功记录。
- 自由文本 question 可保存、用于普通聊天并展示给复核人员；首版不由它自动提取症状、执行急诊分诊、提升临床风险或改变图路由。
- 角色内部工具调用仍受身份、资源范围、超时和调用预算限制；模型输出不能自行授权数据写入或修改发布条件。

### 4. 证据、知识库与解释发布

- 普通私人知识问答与正式诊断证据检索分开授权。正式工作流只检索 CURATED_PUBLIC 且 APPROVED、匹配受控 diseaseCodes/topicCodes 的参考资料。
- 查询改写最多进行一次，只改变查询文本，不扩大受控元数据、访问范围或开启外部网页检索。
- 来源校验在解释生成之前，解释声明校验在草稿之后；未经校验的草稿不得作为正式患者解释发布。
- 参考资料只支持一般疾病信息、风险提示、随访说明和通俗解释，不证明患者级预测、疾病概率或治疗适用性。
- Explanation Snapshot 沿用 NONE → DRAFT → VALIDATED → PUBLISHED，或草稿被 REJECTED、已验证内容被 WITHHELD 的语义。REJECTED/WITHHELD 内容不能发布。
- COMPLETED 必须具有已发布且通过校验的解释快照；COMPLETED_LIMITED 不得携带草稿或仅校验未发布的解释。
- 知识迁移须补齐 .doc 与表格型 .docx 的有效文本抽取。解析失败须明确反馈，不得用空文本、空向量或成功状态掩盖能力缺失。
- 对既有 Chroma 集合、embedding、tenant/database、chunk ID 与数据归属保持兼容；切换期间验证 Python 写入与旧 Java 读取，最终验证 Python Agent 读取。
- 正式证据所需的审核、可见性和受控元数据作为迁移契约落实，不扩展成完整的知识运营平台。

### 5. 两类人工操作

- 医生 IMAGE_QUALITY_GATE 与 FINAL_CLINICAL_REVIEW 分开。质量复核只能允许复用现有推理包继续或要求重传，不能确认疾病预测。
- 最终临床复核沿用不同预测情形的允许决策矩阵；校验权限、领取人和版本，禁止审核自己的病例，禁止覆盖 AI 来源字段或自行更改路由。
- 纠正或无法判断的最终复核保持 COMPLETED_LIMITED 等既有语义，不自动再启动检索循环。
- 用户确认适用于保存正式诊断记录、修改资料和其他 Agent 发起的业务变更；聊天、执行快照、进度、技术结果与审计自动持久化，不逐条询问用户。
- 用户确认绑定已验证用户、目标资源、操作类型、拟写入内容及其版本。批准前展示具体内容，不能只批准模糊的“执行工具”。
- 批准后仍重新检查权限、资源状态、内容版本与幂等键。内容变更或确认过期时要求重新确认，不沿用旧批准。
- 用户拒绝不得执行目标业务写入；重复确认、重试或恢复最多产生一次业务写入效果。
- 医生批准不等于用户批准保存；用户批准也不能越过医生复核、证据校验或解释发布条件。
- 工作流解释发布与正式诊断记录保存是不同动作。内部快照自动保存不意味着已经写入正式诊断记录。
- 旧同步诊断端点继续保持既有兼容行为；本节确认要求作用于新增 Agent 发起的业务操作，不静默改变旧端点。

### 6. 会话、MCP 与接口

- 当前会话历史真实进入后续模型调用。只存数据库或传 threadId 不算实现多轮记忆。
- 历史诊断由授权工具按需查询并标明来源；其他会话的症状、结论不得自动进入本次病例事实。
- 聊天与上传请求使用同一 Workflow 标识和幂等契约；查看同一任务不得重新推理或建立第二份诊断记录。
- 普通知识问答不必启动完整诊断流程。识别出诊断意图后，将用户引导或绑定到受控任务。
- 保留当前 Agent 会话、历史、附件、流式聊天与 MCP 使用场景。具体旧端点以实现前的契约清单为准，不依赖历史文档中不一致的端点总数。
- MCP 服务选择继续校验用户归属、启用状态和连接策略。动态外部工具不能绕过临床门禁、证据范围或用户写入确认。
- 现有聊天 SSE 的终止与错误契约须回归；新增工作流进度、补充信息和确认事件必须携带可关联的会话、任务或操作标识。
- 不向前端暴露可自行选择下一节点或修改内部路由的参数。患者视图不得直接输出未经发布门校验的原始预测或草稿。
- 新异步工作流沿用 POST /api/diagnosis/workflows、202 Accepted 与任务标识的契约；旧 POST /api/diagnosis/diagnosis 保持同步及原响应兼容。
- 旧业务响应继续遵循现有成功信息、错误封装、Long 与日期序列化裁定；新工作流契约不强行套用旧接口“所有错误 HTTP 200”的规则。
- 新增接口覆盖任务状态与事件、必要的补充输入、用户确认与拒绝、医生领取与提交复核。确切 URL、字段和错误码在实现时以现有 release 契约为基线形成 OpenAPI 契约清单。

### 7. 持久化、可靠执行与前端

- 采用数据库持久任务、MySQL 时间租约、fencing token、工作流版本 CAS、至少一次投递与节点幂等。技术失败重试耗尽后失败，不转成临床拒绝或人工复核。
- 外部模型和工具调用在数据库事务之外执行；结果仅在执行者仍持有有效租约与匹配版本时提交。
- 图中断用于等待补充输入、批准或复核后继续执行；生产必须采用可跨进程、跨重启恢复的 checkpoint 存储，不以内存 saver 验收。
- MySQL 业务记录与 checkpoint 各司其职。若 checkpoint 持久适配需要额外依赖，先验证 Python/LangGraph 兼容，不默认引入 PostgreSQL 或第二套业务数据库。
- 数据库升级作为版本化部署资产交付，延续统一的迁移版本治理；不另建 Alembic 版本历史，不由 Web 启动时自动建表，也不改写旧 Flyway 历史或原 Java 源码。
- 对齐 release 的工作流、任务、复核、解释、引用和审计数据语义，并新增用户操作确认所需数据。升级后旧 Java 会话服务必须仍能启动；迁移与回退须在真实数据库验证。
- 审计保留追加事件，记录主体、动作、任务、版本和结果；避免将密钥或不必要的用户原始资料写入日志。
- 前端仅补齐任务进度、补充说明、用户批准与拒绝、医生复核以及恢复连接。保留现有 Vue 技术栈、页面风格和聊天使用方式。
- 聊天页面与诊断页面读取同一任务状态；断流后的界面通过服务端状态恢复，不把本地缓存当成已完成或已保存的依据。

## Testing Decisions

主要测试边界是经过真实路由、身份校验和序列化的 FastAPI HTTP/SSE 接口，以用户可见结果和持久化效果验证流程。它延续已有业务契约测试的方式，并覆盖从入口到存储的边界接线；不以直接调用 helper、检查类名或匹配源码字符串作为完成证据。

在这一主要边界内，模型、算法和外部工具可用可控适配器构造成功、拒绝、超时等输入。状态恢复测试重建应用或进程，复用持久存储；真实服务验收则使用实际 MySQL、Redis、Chroma、Java 会话服务和已验证模型权重。

| 验收编号 | 用户可见行为与判据 |
|---|---|
| AC-01 | 聊天和上传分别发起任务，均经同一工作流服务；同幂等请求只返回同一任务，页面查询不触发新推理。 |
| AC-02 | 无登录、跨用户会话、跨用户任务、跨用户审批和越权工具调用均被拒绝；不能靠传入 userId 扩权。 |
| AC-03 | 当前会话第二轮能使用已提供信息；另一会话的症状不自动进入本次病例，历史查询显示可追溯来源。 |
| AC-04 | 图片通过、拒绝与需质量复核分别走正确路径；质量和影像节点共享同一已提交推理包。 |
| AC-05 | 缺权重、来源校验失败或推理异常不产生成功诊断；技术失败不伪装成安全拒绝或医生复核。 |
| AC-06 | 检索仅使用允许的可见性、审核状态和受控元数据；不足时至多改写一次，范围不扩大。 |
| AC-07 | 来源不合格、声明校验拒绝和解释扣留均不会发布草稿；COMPLETED 与 COMPLETED_LIMITED 符合解释不变量。 |
| AC-08 | 补充输入中断真实等待用户；再次提交后恢复同一交互与任务，不重复处理原输入直至循环耗尽。 |
| AC-09 | 用户批准前不执行拟保存操作，拒绝后仍无写入；批准合法且内容版本匹配后只保存一次。 |
| AC-10 | 重复确认、过期批准、修改内容后批准、跨用户批准和恢复后重放均不会导致非法或重复写入。 |
| AC-11 | 两类医生复核执行各自的决策矩阵；自审、未领取、过期版本和不兼容决策被拒绝；用户确认不能替代复核。 |
| AC-12 | 服务在任务执行中、等待用户确认和等待医生复核时分别重启；恢复后状态一致、审批仍有效且已完成结果不重复提交。 |
| AC-13 | 模拟重复任务、租约失效、两个执行者竞争及重试耗尽；过期执行者不能提交，新任务恢复不复制业务路由。 |
| AC-14 | 实际 SSE 可展示响应和任务事件；断连重连后可从服务端恢复状态，正常结束与错误不会留下虚假的完成界面。 |
| AC-15 | 原业务与 Agent 接口契约回归覆盖 HTTP/SSE 真实响应、分页、字段类型、Long/日期格式、权限及旧同步诊断行为。 |
| AC-16 | 使用真实 .doc 和包含有效表格内容的 .docx，经上传、抽取、入库、embedding 和检索得到有效内容；明确区分空文档与解析失败。 |
| AC-17 | 真实 MySQL 验证事务、版本冲突、租约与受影响行数语义；不能用 SQLite 通过替代这些验证。 |
| AC-18 | 真实 Chroma 与 embedding 验证写入、检索、访问范围和引用；过渡阶段额外验证旧 Java 读端兼容。 |
| AC-19 | 真实 Java 会话服务验证登录、登出、鉴权转发和失效；数据库升级后 Java 仍能启动，Nginx 无端口冲突或代理回环。 |
| AC-20 | 从文档可复现启动、健康检查、逐项切流和回退；回退不遗失已创建任务或审批，也不让两套服务同时执行同一任务。 |
| AC-21 | 前端端到端覆盖上传、聊天绑定任务、拒绝/批准保存、补充说明、医生复核和刷新恢复；必要改动通过类型检查与构建。 |
| AC-22 | 实现具有生产可调用的图注册、任务执行器和完整任务终态；只有单元测试中的图能够运行不算通过。 |

已有测试先例包括 FastAPI TestClient 的契约与实体序列化测试、release 的图分段和审批恢复测试，以及 MySQL checkpoint 跨实例恢复测试。可复用其测试意图，但须把 Python 端验收提升到 API 与实际持久化边界。SQLite 夹具须正确共享内存数据库，不能把测试连接隔离造成的假失败当成业务缺陷。

验证报告分别记录模拟依赖回归、真实基础设施集成、前端端到端和真实模型验证。无相应服务或权重时标记未验证或阻塞，不用 skip 或先前测试数字宣称验收完成。

## Out of Scope

- 治疗方案生成、用药与药物交互、医保编码、FHIR/HIS 对接、通用医疗知识图谱建设。
- 基于自由文本的自动症状提取、急诊分诊或新的临床风险路由。
- 迁移 Java 的三个会话端点、改造 Spring Session 序列化或更换登录体系。
- 修改、删除原 Java 实现，合并整个 release，修改主检出目录，或本次文档交付直接切换生产服务。
- 将每个角色拆成独立微服务，或让总控 LLM 自由改写整个流程。
- 跨所有聊天自动聚合患者事实、未经明确引用导入历史症状，或建立自动长期患者画像。
- 全面 UI 重构、训练新模型、扩充分类任务或以未训练模型解除权重阻塞。
- 顺带修复新闻建档、公开草稿、既有分块等已登记旧缺陷；这些变更需要独立范围与数据兼容方案。
- 向外部 issue tracker 发布、Git 提交、推送、合并或部署；本次授权的交付是 spec 文档落盘。

## Further Notes

### 基线与 ADR 的继承关系

- 继承 release 的 ADR-001 至 ADR-009：辅助诊断定位、MySQL 单一业务事实来源、证据与解释语义、两类医生复核、可靠执行、旧接口兼容、图运行时边界、知识审核与自由文本边界。
- ADR-007 中 Java 图引擎的具体实现由本次已确认的 LangGraph 替代；图决定路由、MySQL 保存业务事实、任务只负责可靠执行、单一推理包等不变量继续有效。
- release 的“冻结”作为原实现的契约基线保留；本次在独立 Python 实现中新增用户操作确认与交互，不改写原 release。任何进一步改变临床状态、复核矩阵或证据含义的需求须另行记录。
- 先前非 Agent 迁移裁定继续适用于原业务接口；本规范新增的 Agent 目标、工作流契约和确认语义不追溯改变旧同步接口。

### 分阶段交付

1. 核对并保存现有非 Agent 迁移成果，排除 OMC 运行状态变更；建立旧接口与 release 工作流契约清单。
2. 验证 LangGraph 持久化、暂停/恢复及任务调度接线，交付从 API 到持久状态的可执行最小闭环。
3. 迁移图片、推理、证据、解释与医生复核职责，补齐用户操作确认、当前会话记忆和必要前端入口。
4. 补齐文档兼容、部署与回退资产，完成真实服务和前端联调；原 Java 保持可对照、可回退。
5. 汇总 AC-01 至 AC-22 的证据。只有必需验收通过才宣称迁移完成；缺模型权重时明确保留真实诊断验收阻塞。

阶段划分是实现顺序，不是减少已确认范围。提交拆分、版本锁定、checkpoint 适配与具体接口字段属于实现任务，不把它们冒充已经完成的决定。

### 已知验证限制

- 2026-10-10 最近一次已记录实测为 406 passed / 5 skipped，Java 编译成功；这是当时非 Agent 迁移的回归结果，不是本规范中 Python Agent 的完成证据。
- 本次 spec 编写没有运行真实模型、启动外部服务、执行数据库迁移或重跑上述全套测试。
- 缺少有效权重及模型来源校验配置时，真实诊断仍然阻塞；训练不在本规范范围内。
- 现有 Nginx 监听端口与 Java 上游端口冲突需在部署交付中消除；单纯路由文本测试不能替代真实启动验证。
- 参考仓库的内存 checkpoint、重复处理原输入的补充信息循环，以及未接入诊断节点的检索服务，不作为现成完成能力迁入。
