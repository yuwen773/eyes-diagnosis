## 0. 为什么有这份文档

`DESIGN.md` 头部写明的冻结规则是三条：

| 情形 | 处理方式 |
|---|---|
| 主动视觉迭代（首页 / 管理端 / 知识库 / 新闻工作台） | **停止**，不再发起 |
| 一般 UI 优化 | **登记 Issue**（#84），不在冻结基线上直接改 |
| 阻断性故障 / 安全修复 | 例外，可修 |

但冻结之后 `ui` 并没有停：截至 `b805377f`，冻结 tag 之后共有 **90 个提交、13 个 PR 合入**。这些放行**只存在于会话记录里，不在仓库里**——于是任何后来者都无法判断某处改动"算不算冻结面、有没有被授权"。

本文件把这笔账补进仓库：**记录实际发生了什么、依据是什么、哪些仍需 owner 裁定**。它不新增规则，也不改写 `DESIGN.md`。

## 2. 口径澄清（冻结 ≠ 分支静止）

| 容易踩的说法 | 准确说法 |
|---|---|
| 「冻结后 `ui` 不再前进」 | **错**。冻结的是**主动视觉迭代**，不是分支。文档、工具、阻断修复、安全修复照常放行；视觉迭代需 owner 放行并在此登记 |
| 「`ui` tip 就是 `6ae633b8`」 | **已过期**。那是第二枚 tag 的位置；当前 `origin/ui` = `b805377f`（2026-11-18） |
| 「冻结 tag 会跟着移动」 | **不会**。`iris-ui-v2.1-freeze-20261115` 固定指向 `80f53f7f`，本文与 `DESIGN.md` 都不得改写它 |
| 「`04ff3ed0` / `f42065e4` 是越权改视觉」 | **不是突然出现的越权**：两笔都在 owner 合并的 PR #91 内，只是当时没有写进任何例外记录。本文补齐 |

## 3. 之后的判定流程（建议）

1. **先归类**：阻断故障 / 安全修复 / 文档与工具 / 视觉迭代。
2. 前三类可直接放行；**视觉迭代**必须在 PR 描述里写明「冻结例外」与改动范围。
3. 合并后在 **本文 §1 表追加一行**（PR 号、日期、类型、一句话依据）。
4. 一般 UI 优化仍走 **Issue #84**，不直接改冻结基线。
5. `DESIGN.md §7` 做状态核对时，同时核对本文的「本登记覆盖到」。

## 4. 仍需 owner 裁定（本文不擅自决定）

**R3 用户端体验（#94 / #95 / #96）与冻结条文的关系。**

- 事实：这三票是**整阶段的视觉重设计**（Agent 工作区、资讯页、判读 / 报告 / 个人中心），由 owner 合并进 `ui`。
- 冲突：`DESIGN.md` 冻结条只给「阻断故障」与「安全修复」两类例外，**没有**授权"某个阶段可以做视觉迭代"。
- 两种收口方式（二选一，需 owner 拍板）：
  1. **承认 R3 是冻结后的正式下一阶段**：在 `DESIGN.md` 冻结条补一句「owner 放行的阶段性视觉工作（如 Iris R3 用户端体验）按阶段登记，不受本条限制」——同时保留"日常主动视觉迭代停止"的语义。
  2. **承认它们是越权合并**：在本文标记为例外，并把 R3 的视觉债登记到 Issue #84，后续不再作为基线复刻。

在没有裁定前，本文件把 #94–#96 记为**已发生、有 owner 合并记录、无条文覆盖**，不称其为"已授权"。
