## 第 4 轮：把「预览就是公开页那篇文章」变成可核对的事实

上一轮视觉复审指出：手机档预览不是公开页的手机版式——设备框只有
`container-type: inline-size`，而 `news.css` 里标题字号、纸面内边距、目录与正文
间距都是 `vw` 派生的，**vw 仍按浏览器视口算**，于是 390px 的设备框拿到的是 1440
视口的尺寸。断点补上了，尺寸没补。

这轮的改法不是再写一套样式，而是**让同一批尺寸在两种上下文里各自成立**：

| 位置 | 公开页 | 管理端预览设备框 |
|---|---|---|
| 标题字号 | `--news-scale-title: clamp(32px, 4.2vw, 56px)` | 同一变量覆写为 `clamp(32px, 4.2cqi, 56px)` |
| 纸面内边距 | `--news-scale-paper-pad: clamp(26px, 3.4vw, 52px)` | 覆写为 `3.4cqi` |
| 纸面量宽 | `--news-scale-paper-max: clamp(52px, 6.8vw, 104px)` | 覆写为 `6.8cqi` |
| 目录与正文间距 | `--news-scale-body-gap: clamp(24px, 3.6vw, 56px)` | 覆写为 `3.6cqi` |
| 眉线 / 封面纵向留白 | `--news-scale-head-pad` / `--news-scale-plate-gap`（vh 派生） | 覆写为 `calc(var(--news-sim-vh) * …)`，模拟视口高度写明（桌面 900 / 手机 844） |

`1cqi` = 设备框宽度的 1%，与 `1vw` = 视口宽度的 1% 等价——**设备框多宽就等于模拟
多宽的视口**。公开页的值逐字未变（仍是 vw/vh），公开页外观零变化。

核对脚本 `admin-news-preview-parity.mjs` 用**同一篇文章**（库里已发布文章）在两个
上下文里量计算样式，逐项比对（容差 0.6px），本轮退出码 0：

> 这一版的核对只覆盖**计算样式**，量不到渲染出来的列宽与断行；第 5 轮把脚本换成量
> **渲染结果**（见上），下面的表因此只作为历史记录保留。

| 量 | 手机档：公开页 390 视口 | 预览 390 设备框 | 桌面档：公开页 1020 视口 | 预览 1020 设备框 |

## 第 5 轮：把「同宽即同版式」从计算样式核到**渲染结果**

第 3 轮独立复核（`pr-b-verify-3`）指出两条，前一轮的证据撑不住这个主张：

- **F1 设备框自己占布局**：机身边框与内边距吃掉了「模拟视口」的宽度——同为 390，
  公开页正文列宽 342px，预览里只有 324px，同一段话少排一行；读数写着「模拟视口 390」，
  实际排版宽度却是 360，自相矛盾。
- **F2 核对脚本只量计算样式**：`getComputedStyle` 返回的是字符串，原脚本那条「数值容差」
  分支是死代码；而**渲染出来的列宽与断行**根本没量。另外库里 13 篇已发布文章没有一篇
  带章节或封面——目录与封面这两条路径在公开页上根本没被走过，量不到。

### 改法

**设备框改成「它自己就是被模拟的视口」**：机身边框用 `box-shadow` 画（不占布局——边框若
占布局，同宽下正文列宽就少 2px，断行随之不同，「同一篇文章」就不是同一张纸了）；设备框
内层 `.admin-newsedit__device-page` 复刻公开页 `.wrap.news-detail` 的页边距（>600 档
40px、≤600 档 24px，与 `--gutter` 同档）与纵向留白（按声明的模拟视口高度）。

**核对脚本重写为量渲染结果**：文章宽 / 纸面宽 / 正文列宽 / 目录列宽 / 网格列数 /
**每段行盒数**（用 `Range` 取行盒、按 distinct top 计行）逐项比对，容差 0.6px。
夹具改为脚本自建的一篇**临时发布**文章（多级标题 + 引用 + 列表 + 真上传的封面），
采集结束删除，脚本收尾打印删除回执。

## 第 6 轮：把「暗色证据」修成**真暗色**，并把同值核对扩到双主题

第 5 轮复审（`pr-b-verify-3`）指出一个证据本身不可信的问题：两张标着「暗色」的图
（`preview-complex-desktop-1440-dark.png` 与 `public-news-1440-dark.png`）与各自的
浅色图**逐字节相同**——它们根本不是暗色。

### 根因：主题开关在登录页不存在，而脚本是「点一下试试」

采集脚本原本这样切主题：

```js
const t = page.locator(".theme-toggle")
if (await t.count()) await t.click()   // 计数为 0 → 静默跳过
```

`.theme-toggle` 只存在于 `AdminLayout.tsx`（后台外壳）与 `ProductHeader.tsx`（产品页
顶栏）。**登录页没有这个按钮**——脚本登录后停留在登录页切主题，`count()` 返回 0，
`if` 直接跳过，主题从未切换；于是拍下来的「暗色」是浅色图的副本，而脚本一路绿灯。

这是一类典型的**无声失败**：条件不成立时不是报错，而是「什么都没发生」，证据看起来
齐了，实际什么都没证明。

### 改法：写 localStorage + 重载 + **硬断言**

| 位置 | 改法 |
|---|---|
| 三个采集脚本 | 统一 `setTheme(page, theme)`：写 `localStorage["theme"]`（键见 `theme-provider.tsx`）→ 重载 → **断言 `html.dark` 存在 / 不存在**，不成立就抛错 |
| 截图前 | 名字以 `-dark` 结尾的截图，截图前再断言一次 `html.dark`；浅色图断言 `html.dark` 不在 |
| 核对脚本 | 测量循环扩成 **浅色 × 暗色** 两轮，两轮各自出图并逐项比对 |

断言是关键：**把无声失败变成硬错误**。现在主题没切过去，脚本会带着
`主题没切到暗色：html.dark 不存在` 退出，而不是拍出一张浅色图冒充暗色。

### 复采结果

- 深色图与浅色图不再逐字节相同（`preview-desktop-1440-dark.png` 与
  `preview-desktop-1440-light.png` 哈希不同，肉眼可见品牌画布、纸面、目录、正文
  层级均已翻到暗色）；
- 核对脚本浅色、暗色**两轮都退出码 0**，两轮的量值逐项相同（暗色只换配色，不换
  版式——这正是「双主题一致性」要证明的事）：
  - 手机档 390：文章宽 342 / 纸面 342 / 正文列 304 / 目录 342 / 段落行盒 5-4-5-2-2-2-2-5；
  - 桌面档 1020：文章宽 940 / 纸面 635.45 / 正文列 564.11 / 目录 220 /
    网格 220px 683.28px / 段落行盒 3-2-3-1-1-1-1-3。
- 对应截图新增：`parity-preview-mobile-dark.png`、`parity-preview-desktop-dark.png`、
  `parity-public-mobile-dark.png`、`parity-public-desktop-dark.png`（情形 B 的
  `parity-preview-dirty.png` / `parity-public-after-save.png` 也显式固定在暗色，
  两侧同主题才可比）。

## 已知取舍

1. **眉线按发布状态走**：只有 `status=1`（已发布）才沿用真实发布时间；草稿 / 待审核 /
   下架即使带着 publishTime 也一律显示「预览稿 · 尚未发布，公开页不会出现」——
   旧逻辑看 publishTime 存在性，会让待审核 / 下架文章冒充「已上线」。
2. **摘要不是独立字段**：后端保存时按「剥标签后的正文前 30 字」生成摘要，表单里没有
   摘要输入框。预览显示的是**保存后将写入的**那 30 字，不足 30 字时如实说「保存会被
   拒绝」，不虚构一个摘要字段。库里老文章的摘要是当年手写/旧规则生成的，
   与「保存后摘要」不同时两者并列显示，不假装它们一样。
3. **预览时收起右侧发布设置栏**：编辑区两栏只有 676px，塞不下公开页 900px 以上的
   桌面版式。切到预览把右栏收起（与有没有未保存修改无关），提示语无条件写明这一点，
   保存按钮仍在工具行；右栏里的「未保存」读数因此在预览中不可见，未保存状态改由
   预览条单独一句「当前有未保存修改」承担。
4. **同宽即同版式（可核对）**：预览设备框宽度 = 模拟的视口宽度，断点与尺寸都按它算，
   因此「设备框 390px」与「公开页 390px 视口」逐项同值——由
   `admin-news-preview-parity.mjs` **量渲染结果**核对（列宽、目录列宽、每段行盒数、
   网格列数，容差 0.6px）。断点档位（900 / 768）与 `news.css` 的媒体查询一一对应。
   设备框自身不再占布局（机身边框用 `box-shadow` 画），内层页边距复刻公开页 `.wrap`
   的 `--gutter`——同宽下正文列宽逐像素相等。
5. **纵向留白按声明的模拟视口高度算**：文章眉线、封面下方间距原本是 `vh` 派生的，
   容器没有对应的纵向单位。预览里写明模拟高度（桌面 900 / 手机 844）并据此换算，
   不让它们继续按管理员浏览器窗口的高度变化。
6. **桌面预览宽度受管理端版型限制（如实记录）**：管理端 1440 视口下工作区主列约
   1020px（侧栏 248 + 管理端内边距），设备框再宽也受父容器限制——所以「桌面」档
   模拟的是 1020px 视口，不是 1240px。预览条实时写出当前模拟的宽度，别让人以为
   按钮写着「桌面」就一定是桌面宽度。组件与 CSS 与公开页仍是同一份。
7. **目录在预览里不吸顶**：预览画布没有真实滚动容器，`position: sticky` 无处可粘，
   目录一律 static（公开页桌面端是 sticky）。只影响目录的吸附，不影响版式。
8. **摘要读数口径**：显示「剥标签后正文前 30 个字符」，与后端 `buildSummary`
   同管线；Markdown 预览里 `&amp;` 类实体在渲染时被还原，字数与后端对已落库
   HTML 的统计最多差在实体字符上（`NewsArticleView` 文件注释有写）。
9. **字数按渲染后全文算**：Markdown 源的 `#`、`**`、`-` 记号不计入字数，与公开页
   「数库里存的 HTML」同口径；被提走的导语与挤出正文的标题仍在全文里，不多算
   也不少算（单测断言 402 / 483 两个真实读数）。
10. **同屏两个数字是两种口径，不是少了几十字**：文章眉线的「N 字」是公开页同口径的
    `newsWordCount`（汉字按字、拉丁按词）；编辑区那一侧的「N 字符」是后端
    「正文至少 30 字」守卫用的可见字符数（剥标签后的正文长度）。所以同屏 154 字符
    对 135 字是正常的——两边服务的目的不同。界面因此把编辑器侧一律写成「字符」，
    并在该读数上挂口径说明，不让两个「字」混在一起。
11. **作者兜底两侧不同**：作者取库里 `author` 字段（两侧同源）；公开页缺作者时
    显示「编辑部」，管理端预览显示「未署名」——预览面对的是还没发布的稿子，
    「未署名」比「编辑部」诚实。这是唯一的文案差异，不影响版式。
12. **目录的吸附行为两侧不同（已知、有意）**：公开页桌面端目录是 `position: sticky`，
   预览画布没有内部滚动容器，`sticky` 会粘到浏览器视口、跑到设备框外面去，所以预览
   一律 `static`。核对脚本把这一项记为 NOTE 而不是失败——它影响的是滚动时的吸附，
   不是版式（目录列宽、行盒数、网格列数仍逐项同值）。
13. **核对脚本的临时素材只清库、不清对象存储**：对照稿的封面是真实上传到对象存储的
   临时图片，删除新闻不会连带删除那个文件——库里不留记录，对象存储里会留一个孤儿
   对象。脚本收尾打印删除回执，如实记录这一层残留。
14. **预览模拟的视口上限是 1240px，宽屏访客的两档差异复现不了**：设备框
   `max-width: 1240px`，因此预览能模拟的最宽视口就是 1240px。而公开页在
   **≥2200px** 的视口上会同时切走两档——`--maxw: 1760px`、`--gutter: 56px`
   （`tokens.css` 的 2200 断点），标题字号 `clamp(32px, 4.2vw, 56px)` 在 1240px
   时算到 52.08px、在 2200px 时到顶 56px。也就是说：1440–2199px 的访客看到的
   版式预览能复现（`4.2vw` 仍在同一档），2200px 以上的访客会看到**更大的标题与更宽的
   版心**，这两档预览模拟不出来。预览条写明的「模拟视口 N × H」里的 N 就是当前
   模拟值，不会假装自己覆盖了宽屏档。
