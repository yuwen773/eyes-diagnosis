# 患者围绕已发布结果追问（#23）

对应 [#23](https://github.com/yuwen773/eyes-diagnosis/issues/23)，依赖 [患者分层解释](patient-explanation.md)。这里的“已发布”沿用 #21 的读取条件：本人任务、医生批准、冻结材料一致且本次来源校验通过。医生批准及追问均不构成患者保存授权。

## 患者操作与回答范围

在任务页打开获准说明后，可以输入关于本次结果的问题。系统从已发布的患者声明及其精确冻结来源片段中匹配词语，返回相关声明、原引用及来源版本；中文采用既有分词器。匹配只表示内容相关，界面明确说明它不构成新的诊断，也不代表问题的全部内容已获回答。

没有匹配时返回“未找到与问题匹配的依据”，不补写推测。当前实现为确定性的原文查找，不调用模型、普通私人知识库、聊天历史或其他临床资料；不会扩充医生批准的解释。未匹配的声明和未被回答引用的来源不返回。

一般眼健康咨询通过清晰标注的独立链接进入既有 `/agent` 聊天，不自动携带本次结果、引用或问题。普通聊天内容不作为本次受控临床证据。追问没有持久化历史，不新增数据库表。

## 每次请求的安全边界

每次请求独立验证登录身份及任务归属。其他患者、医生、管理员、资料审核员都不能因角色读取他人的结果。未发布、拒绝、受限、来源撤回或冻结材料变化时返回受限路径，且不含声明或来源。

复用医生门禁的来源、任务及材料锁；锁内重新检查精确文档及治理版本、资格、疾病和主题范围、片段完整性、推理输入、快照和全部冻结材料。等待锁的追问读取已提交的新状态。追问采用独立的只读调用方式：拒绝后也不改变任务状态或版本、快照、草稿、医生决定、授权候选、正式记录及回执。#21 读取和 #22 保存继续使用原有的失效处理。

患者页以纯文本显示说明及来源；追问开始时清理旧回答。切换账号或任务、刷新、保存检查、关闭和卸载后，迟到响应不恢复旧回答。追问受限、请求失败、任务不符或未知状态时关闭旧说明，要求重新打开任务核验。

## HTTP 接口

`POST /api/diagnosis-tasks/{id}/follow-ups`，请求为 `{"question":"关于本次结果的问题"}`，问题须为 1–1000 个字符且不能全空白。服务端仅使用登录身份，不接受客户端指定的患者、证据集或发布状态。

响应沿用 `BaseResponse`，设置 `Cache-Control: no-store`。`data` 包含 `taskId/status/message/claims/sources`：

| status | 内容 |
|---|---|
| `RELATED_INFORMATION` | 已发布相关声明及它们引用的原来源；保留逐声明引用索引 |
| `INSUFFICIENT_EVIDENCE` | 固定无依据提示，声明和来源为空 |
| `RESTRICTED` | 固定受限提示，声明和来源为空 |

不存在或不属于本人返回业务码 `40400`，未登录 `40100`，问题无效 `40000`。无自动保存、重新推理、重新复核或重新发布操作。

## 工程验证

用户确认的测试边界为公开患者 HTTP API 和患者页面交互，使用隔离 MySQL、合成数据及受控身份。`PatientFollowUpApiTest` 共 37 项；测试账号为专用合成 `issue23`，数据库 URL 须严格匹配 `jdbc:mysql://127.0.0.1:<port>/issue23_test`。套件会清空该专项库内相关表，不能指向业务库。

设置 `ISSUE23_TEST_URL` 后执行 `mvn -Dtest=PatientFollowUpApiTest test`，再运行 `python scripts/check_surefire_skips.py target/surefire-reports issue23`。未配置时明确 opt-in 跳过，不算验收。CI 的 `issue23-mysql` 作业要求全部例数及零跳过。真实模型、真实医学资料领域审核、临床与生产验收另行记录。
