# 影像存储失败语义（ADR-lite）

- 日期：2026-11-17
- 范围：`DiagnosisServiceImpl.doDiagnosis` + `FileManager` 的判读影像写入路径
- 状态：已实施（无数据库迁移、无 API 形状变更）

## 1. 问题

`doDiagnosis` 的旧顺序是：推理 → 上传对象存储 → 落库。上传那步是：

```java
try { uploadPicture(...) } catch (Exception e) { log.error("COS upload failed", e); }
```

对象存储超时 / 鉴权失败 / 5xx 都会被吞掉，然后照常写一条 `t_diagnosis` 记录。
结果是**有判读结论、有记录 ID、没有原图**：报告页没有证据影像，复核时无法回放，
而界面当时给出的仍是成功态。

## 2. 需要回答的不变量

| # | 问题 | 结论 |
|---|---|---|
| 1 | 影像上传失败是否允许产生正式判读记录？ | **不允许**。正式记录承诺「影像随记录保存」，兑现不了就不能落库 |
| 2 | 若允许，是否需要「存储失败 / 记录不完整」状态？ | 本轮不引入，见 §3 方案 B |
| 3 | 如何避免虚假的完整归档？ | 存储失败 → 请求失败，不写记录 |
| 4 | 推理完成但存储失败，前端如何感知？ | 收到**独立的 `STORAGE_ERROR(50002)`** 码与「本次判读未归档，请重试」文案，前端据此说「影像没有保存下来」（而不是笼统的「服务没响应」），并保留重试入口 |
| 5 | 存储成功但落库失败，是否残留孤儿对象？ | 会；已加补偿删除（§3 方案 A 第 2 条）。补偿范围覆盖**上传之后的全部工作**（VO 构建 → 证据写回 → 插入）；`save()` 返回 false（插入 0 行）也按失败处理并补偿 |
| 6 | 重试是否产生重复记录 / 重复对象？ | 失败的那次不落库，重试只产生一条；重复对象由补偿删除兜底。**双击并发提交仍可能产生两条记录**（无幂等键），登记为已知限制 |
| 7 | 网络超时 / 取消时服务端是否已完成保存？ | 与旧行为一致：请求到达服务端后仍会跑完；客户端断开不影响落库。未新增事务语义 |
| 8 | 权限与归属保护是否完整？ | 不变：上传前缀按 `loginUser.getId()` 隔离，读取走 `getOwnedDiagnosis` |

> **范围限定**：本 ADR 的不变量只覆盖 `t_diagnosis` 这条「正式判读记录」路径。
> 新合并进来的影像任务路径（`/api/diagnosis-tasks/*`）在存储失败时仍会落一条
> `RESTRICTED` 任务行——那是另一种生命周期，口径以 `docs/diagnosis-task.md` 为准。

## 3. 方案比较

**A. 失败即终止（选用）**

1. 上传失败 → 抛 `BusinessException(STORAGE_ERROR(50002), "影像存储失败，本次判读未归档，请重试")`，
   **不落库**。用独立错误码而不是复用 `SYSTEM_ERROR`：前端要能把「影像没存下来、可以重试」
   与笼统的「服务没响应」分开说。
2. 落库失败（含 `save()` 返回 false）→ 用刚拿到的 object key 补删除刚上传的对象，再把原异常抛出去。
   补偿范围覆盖上传之后的全部工作，不只是 `save()` 那一行。
3. 校验失败（体积 / 格式 / 空文件）原样上抛，不包装成「存储失败」。

代价：推理结果不返回给用户。缓解：推理缓存已按图片哈希先行写入（指纹完整时），
同一张图重试命中缓存，不重复推理。指纹不完整时缓存关闭，重试会重算一次——可接受。

**B. 落库但标记「影像未归档」状态**

需要新增列 / 状态机、迁移、管理端对账，并回答「未归档记录能否作为诊疗依据」。
属于医学业务政策，超出本轮授权，未采用。若产品决定保留无影像结论，应另起
迁移专项（`V*__diagnosis_archive_state.sql`）并同步列表 / 报告 / 复核队列。

**C. 先上传后推理**

存储失败时省掉一次推理，但推理失败会留下孤儿对象；整体并不更安全，未采用。

## 4. 与未来 S3 兼容抽象的关系

补偿删除依赖 `FileManager` 返回的 object key，不依赖 COS 专有 API；迁移到 S3 或
其它 S3 兼容存储时，只需保持「上传返回 key」与「按 key 删除」两个原语。
`FileManager` 仍是唯一的图片写入口，未在业务代码里直接使用 COS 客户端。

## 5. 回滚策略

本次没有数据库变更，回滚 = 还原这些文件：`DiagnosisServiceImpl` / `FileManager` /
`UploadPictureDetail` / `ErrorCode` / `FileConstant`，前端 `web/src/lib/faults.ts`
（去掉 `50002` 分支即可）。已上传对象不受影响；补偿删除只作用于
「本次请求刚上传、且落库失败」的对象。
