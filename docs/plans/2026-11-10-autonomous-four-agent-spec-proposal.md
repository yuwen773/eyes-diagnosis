# 四 Agent 自治协作正式流程变更提案（B）

日期：2026-11-10。

状态：**用户已确认；代码和本次专项验收已完成。** 结果见 [2026-11-11 验收记录](../testing/2026-11-11-autonomous-four-agent-acceptance.md)。本文作为定向变更规格，真实模型反馈、临床和生产验收仍须按各自范围判断。

## 1. 基线与变更目标

工作树为 `worktree-java-multi-agent-arch`，核对时 HEAD 为 `74cf7d8246c6fb30ad58bd0497f8e08f94be749f`。基线包含交接中的未提交运维入口、V16 计时和三个协作视图；算法 OOD 等其他未提交工作须保留。

当前 `PatientDraftCoordinator.run()` 同步串联 Vision → Evidence → Explanation → Critic。四角色系统提示和输出类型独立，但共享无历史模型传输，没有各自收件箱或会话。② 的 `AUTONOMY_EVENTS` 是播放常量。

本变更将新任务改为**受约束的自治协作**：四角色拥有任务内独立状态和收件箱，接收经过校验的结构化消息后推进；Vision 与 Evidence 的首轮工作可同时执行；Critic 根据实际草稿决定是否请求补证或重写。管理员泳道读取真实调用与消息，不以预设事件伪装运行。

自治权限限定为各角色的业务判断、检索查询及补证/重写请求。调度、消息发送者身份、允许收件人、调用预算、证据资格、版本和最终状态由 Java 控制。无依赖的工作才并行，Explanation 与 Critic 的材料依赖仍然必须满足。

本轮不扩展正式 `/agent` 聊天、不执行图像再分析、不更换 Agent 框架、不引入外部消息中间件。已有 Spring AI 模型传输复用，但每次请求显式构造角色上下文，不使用跨任务共享聊天记忆。

## 2. 对既有冻结规格的定向修订

确认后更新 `docs/patient-draft.md` 的「独立角色」「冻结、反馈和停止」「运维试验台」「验证」。既有战略 ADR 中的 Graph、重推理和无限自治候选不因本提案而获准实施。

| 方面 | 现有契约 | B 的新契约 |
|---|---|---|
| 首轮调度 | Evidence 必须等待 Vision | Vision 与 Evidence 同时获得同一获准推理摘要，独立开始 |
| 角色状态 | 无历史调用 | 每个任务、角色有独立收件箱与已处理消息状态；每次模型调用只接收该角色获准材料 |
| 信息流 | 协调器局部变量传参 | 持久化、可定位、按角色寻址的结构化消息，接收者记录实际消费的消息 |
| 反馈 | 协调器读取 Critic 结果后直接调用 | Critic 输出受校验后形成发往 Evidence/Explanation 的请求，接收角色消费并执行一次反馈 |
| Explanation 证据输入 | 完整 Citation，含标题和来源 | 模型只接收 `citationIndex`、`excerpt` 与证据版本；完整来源继续冻结并供医生核查 |
| 管理员视图② | 定时播放常量 | 选择实际任务，显示真实起止、消息去向、版本、异议和修订；支持真实轨迹重播 |

Evidence 首轮的模型上下文明确允许没有 Vision 结果；不能伪装为已看过 Vision。Vision 完成后将摘要与限制送入相关角色收件箱。Evidence 首轮检索只依赖推理摘要和服务端固定的疾病/主题范围；迟到的 Vision 摘要本身不额外触发一次模型请求，其限制必须由 Explanation 和 Critic 使用，必要时由 Critic 请求补证。

独立会话指任务内的角色状态与消息历史隔离。Explanation 修订时可看到本角色先前草稿和有效异议。Critic 每轮仍重新检查当前推理、Vision、冻结证据和草稿，**不把上一轮 Critic 结论作为模型上下文**，以保留独立复核约束。服务器保留全部历史供审计。

## 3. 角色消息与调度契约

每条已接受的角色消息包含以下由服务端绑定的信封信息：

- `messageId`：任务内唯一标识。
- `taskId`、`workflowVersion`：规范任务 ID 与流程版本。
- `senderRole`、`recipientRole`、`kind`：发送者、收件人和消息类型。
- `sourceSequence`、`causationMessageId`：来源模型调用与直接原因；初始启动无原因消息。
- `inferenceDigest`、`evidenceVersion`、`draftVersion`：材料绑定，不适用的版本为 null。
- `payload`：经现有类型及新增消息契约校验的业务材料，不含原始思维链。

模型不能自行签发信封、选择任意任务或越权收件人。发送者身份来自执行中的角色；路由由已校验输出映射至下表。不是用另一个模型作总控，也不增加纯调度 LLM 调用。

| 发送者 | 收件人 | 消息及作用 |
|---|---|---|
| Vision | Evidence、Explanation、Critic | `VISION_READY`：推理摘要与限制，供收件箱按依赖消费 |
| Evidence | Explanation、Critic | `EVIDENCE_READY`：已冻结证据版本；只有冻结成功才发送 |
| Explanation | Critic | `DRAFT_READY`：通过确定性校验并保存的草稿及其证据版本 |
| Critic | Explanation | `REWRITE_REQUESTED`：可定位异议，启动唯一一次修订 |
| Critic | Evidence | `SUPPLEMENT_REQUESTED`：可定位异议，启动唯一一次补证；新证据到达后驱动修订 |
| Critic | 终态门禁 | `REVIEW_COMPLETED`：当前草稿无异议；只请求服务端复验，无批准或发布权 |

四角色各有一个任务内收件箱，同一角色同一材料版本最多执行一次；只有获准、未消费且材料绑定一致的消息能驱动动作。按依赖合并消息，不能收到一个通知就重复调用模型。重复投递不增加模型调用；未知角色、非法路由或版本冲突须记录并停止，不静默解释成成功。终态后的重复/迟到事件不得改变终态或追加材料。

Explanation 首轮必须同时拿到有效的 `VISION_READY` 与 `EVIDENCE_READY`；Critic 必须拿到匹配版本的 `DRAFT_READY` 及全部对应材料。反馈只适用于当前被检查的草稿；旧证据/草稿版本的反馈不能触发新执行。

同一任务最多两个模型请求在途，首轮 Vision 与 Evidence 的重叠需由运行证据证明。执行器全局容量与队列有界；容量不足时记录 `MODEL_BUSY` 并受限，不能改为无限排队或重试。收件箱控制逻辑不得占住模型执行线程后再等待该线程池中的子任务。

## 4. 预算、停止与一致性

保持既有上限：**每任务 8 次模型调用、总计 90 秒、每次 20 秒、最多补证一次、最多重写一次**。仍只允许一轮反馈：首次复核要求补证时，补证和随后的修订合计为这一轮；第二次复核再次提出任何异议即 `FEEDBACK_LIMIT`。

| 成功路径 | 模型调用数 |
|---|---:|
| Vision + Evidence 并行，Explanation，Critic 无异议 | 4 |
| 首次 Critic 要求重写，Explanation 修订，Critic 复核 | 6 |
| 首次 Critic 要求补证，Evidence 补证，Explanation 修订，Critic 复核 | 7 |

消息投递、检索结果冻结和确定性校验不消耗额外模型调用。8 次是不可突破的上限，不要求用满额度。并行失败可能使已发出的另一角色请求仍计费，因此失败场景的调用数不保证与旧顺序流程相同。

每次请求前，以 `task → run` 一致锁顺序在事务内预扣调用数并记录 `STARTED`；两个并发请求不能读到相同额度或调用序号。失败、提交执行器被拒、取消、响应未知均不退额度。单次时限从实际请求执行起计，总截止时间从领取任务时起计，排队不能延长总截止时间。

任一角色失败后统一关闭运行、取消兄弟请求并停止消费消息。已发出的请求无法保证提供方停止计算；迟到输出不能写入结果、投递消息或放行任务。保留既有 `PROVIDER_AUTH`、`PROVIDER_RATE_LIMIT`、`PROVIDER_UNAVAILABLE`、`INVALID_OUTPUT`、引用/来源/时间/预算停止分类；新增非法消息路由和材料版本冲突的明确原因码并更新管理员文案。

进程崩溃沿用现有保守恢复：不自动重放外部调用，不重置额度，不跨进程续写角色会话；到期后进入 `INTERRUPTED_OR_TIMEOUT`。不能声称供应商请求 exactly-once。

## 5. 引用、冻结与下游兼容

六区段、逐声明引用、非空逐字子串、服务端绑定疾病/主题、受控来源资格与持锁复验保持有效。Explanation 的模型输入缩减不改变服务端完整 Citation、冻结证据格式或医生可见来源。

无效引用仍在确定性校验时立即受限，不为了呈现 Critic 修订动画而先放过无效草稿。Critic 异议→修订的工程测试使用已经通过结构及引用校验、但有可定位内容问题的草稿。更改输入仅用于减少引用元数据的诱因，不据此宣称真实模型引用可靠性达标。

完成前必须保证：四角色所需结果均完成、最终 Critic 与最终草稿/证据版本匹配、无待执行反馈、全部冻结来源仍有效。随后在持锁复验事务内原子提交 `REVIEW_READY` 和任务等待复核状态；`REVIEW_READY` 仍不是批准或发布。

`DoctorReviewService.freeze()` 当前按 `sequence,role,state,output` 冻结消息并计算材料摘要。新增信封、收件引用和角色结果放入该 `output` 内，一并进入既有冻结材料和摘要；不能只存在浏览器内存或未被摘要覆盖的独立事件表。角色上下文中保存实际消费的消息 ID 与版本，使医生可回查每次复核所依赖的材料。

保留旧记录的序列化内容及既有医生材料摘要算法。不得给历史消息回填新字段后导致历史批准失效。终态后禁止修改/追加影响冻结材料的协作消息。患者进度仍来自服务端固定业务文案，不透出模型消息、异议、内部草稿或身份信息；#20 医生授权与自我复核限制、#21 每次读取复验、#22 授权与原子保存继续成立。

## 6. 持久化和模块设计

保持外部 Interface：`PatientDraftCoordinator.run(taskId)`、`runPendingOnce()`、`inspect(taskId)`。可信调用方和后台轮询继续使用这些入口，管理员触发同样走正式流程。

在 `patientdraft` 模块内部，将角色调度与收件箱放到一个自治运行实现中，由协调入口负责领取与接入；预算、证据和终态一致性由同一组持久化操作维护。角色模型请求依赖现有 ChatModel Adapter，测试仅替换外部模型/时钟，数据库使用隔离 MySQL。避免同时保留两套可被生产选择的顺序/自治 runner，也不为每个动作建立单用途抽象层。

新增 V17 迁移（实施前再次核对迁移 head），只做增量修改：运行记录增加 `workflowVersion`。历史记录标识为 `SEQUENTIAL_V1`，新领取任务明确写入 `AUTONOMOUS_V2`。协作信封放入现有消息 JSON，不另建聊天表或患者消息接口。消息序号表示调用预扣顺序，时间戳表示实际开始/完成时刻，不能靠序号伪造并行完成先后。

已有进行中的旧流程不切换版本、不自动重跑；部署切换前应停止旧进程接单并等待旧运行结束，或按既有到期规则受限后再切换。历史完成/受限记录继续可读。回滚不删除迁移或覆盖记录；关闭接单后停止新版本运行，旧程序不得消费未知 `workflowVersion`，须通过兼容性检查避免不兼容二进制回滚。

现有 `eye-diagnosis.draft.enabled` 仍默认关闭；启用后新任务采用正式自治流程，不增加实验专用开关。管理员轨迹入口仍由现有独立开关控制且仅管理员可用。

## 7. 前端外部行为

② 使用所选任务的实际轨迹，轮询复用现有管理员接口；首版不增加 SSE。泳道按真实 `startedAt/completedAt` 与消息信封呈现并行、交接、异议、修订及受限原因。运行结果不能硬编码成“达成共识”。

①、③ 同样处理同一角色多次调用和非顺序完成。现有 `buildStages()` 以角色 Map 留最后一条记录的实现不能承担完整反馈轨迹，须保留每次执行及其版本。①可保留角色摘要，但交接与历史必须与真实调用一致。

历史 `SEQUENTIAL_V1` 任务标为历史顺序流程；缺少消息信封的数据不能补造自治消息。删除生产页面中的 `AUTONOMY_EVENTS` 及定时概念播放；真实轨迹重播只改变播放进度，不再调用模型。

切换任务、退出管理员身份、卸载页面时清空旧材料并停止轮询，丢弃迟到响应。按 `DESIGN.md` 实施并检查明暗主题、窄屏、键盘操作及文本渲染。

## 8. 待确认的测试接口与验收

采用以下 Interface 作为测试 Seam；不增加仅供测试访问的内部调度接口：

1. `PatientDraftCoordinator.run/inspect/runPendingOnce`：真实隔离 MySQL、可控外部模型与时钟；验证角色消息、并行、反馈、预算、来源、迟到输出、崩溃和重放行为。
2. 现有管理员轨迹 HTTP 接口及协作页面公开交互：验证权限、真实轨迹、任务切换、注销和轮询失效处理。
3. 既有 #20 医生复核、#21 患者解释、#22 保存授权 HTTP Interface：验证自治材料可正常冻结/批准/读取/授权保存，材料变化、来源撤回和身份不符仍拒绝。

按单个行为进行 red → green，不批量先写实现耦合测试。沿用既有安全用例，按新契约调整依赖“固定顺序”的替身，不能删除反例来获得全绿。

| 验收项 | 必须观察到的证据 |
|---|---|
| 真实并行 | 模型替身用同步屏障证明 Vision、Evidence 两个请求都进入后才允许返回；不靠易抖动耗时猜测 |
| 角色隔离与因果 | 外部模型收到的实际上下文只含本角色材料，收件消息及版本可从 inspect 回查；无身份、对象地址或跨任务消息 |
| 消息与反馈 | Critic 请求驱动正确收件人；重写/补证/再次复核版本一致，重复事件不会多调用，重复异议受限 |
| 竞态与预算 | 并发任务领取、大小写任务别名、预扣额度、重复投递、消息版本冲突不绕过上限 |
| 停止 | 角色失败取消兄弟请求；超时、断进程、来源变化、迟到输出均不能放行或修改终态 |
| 引用 | Explanation 实际请求不含标题/来源；拼接引文、错误索引及不完整区段仍被拒绝 |
| 医生与患者 | 新增消息字段进入医生冻结摘要；新旧记录可读，旧批准不因迁移失效；患者看不到内部协作材料 |
| 迁移与门禁 | 空库迁移及 V16→V17 升级通过，既有迁移不变；报告计数与跳过门禁同步，新专项及受影响 #20–#22 套件零跳过 |
| 页面 | 单元测试、类型检查、改动文件 lint；浏览器实际点击任务/视图/重播，核对并行、修订、受限、明暗主题及窄屏 |

真实提供方验证纳入本提案的确认范围：最多 **2 个合成任务，合计最多 16 次外部模型调用**，每任务仍按 8/90 秒/20 秒限制；不使用真实患者数据。沿用已配置模型，密钥仅取本机环境变量，不输出、不入库。思考模式采用现有已验证的关闭配置，并记录实际配置、调用数和失败样本。

真实模型是否提出异议不预先保证；用确定性模型验证反馈路径，以真实模型记录实际结果，不能伪造 Critic 意见。若 2 个任务均受限，保留失败证据，不自动追加付费重试，也不声称已验证真实模型成功协作。工程测试、真实提供方、临床及生产证据分别报告。
