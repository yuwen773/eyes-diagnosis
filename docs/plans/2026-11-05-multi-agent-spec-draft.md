# 面向患者的四 Agent 眼底诊断辅助规格（待确认测试边界）

## Problem Statement

患者上传眼底图片后，需要理解模型分析、受控医学依据和下一步提示；现有聊天 Agent 和图片推理能力尚未组成可追溯、多角色协作、受医生及患者授权约束的完整流程。患者不应把模型预测或未审核的 AI 草稿当成确诊。

## Solution

保留现有聊天和普通诊断入口，新增面向患者的诊断辅助流程：调用 Python 眼底图像推理，四个职责独立的 Agent 在可靠协调层下协作，由确定性安全门控及必要的医生复核决定患者可见内容；患者单独授权后才保存正式记录。第一版面向演示和工程验证，不构成临床或生产验收。

## User Stories

1. As a 患者, I want to 上传眼底图片并创建任务, so that 我能获得本次图片的分析。
2. As a 患者, I want to 知道图片是否可用, so that 我能在质量不足时重新上传。
3. As a 患者, I want to 查看分析进度, so that 我知道系统正在处理什么。
4. As a 患者, I want to 看到简要 Agent 工作说明, so that 我理解协作阶段而不误读未审核草稿。
5. As a 患者, I want to 在图片或模型失败时收到清楚提示, so that 我不会误以为结果正常。
6. As a 患者, I want to 在医生复核期间看到等待状态, so that 我知道结果尚未获准发布。
7. As a 患者, I want to 首先看到简洁的结果、风险和下一步提示, so that 我能快速理解信息。
8. As a 患者, I want to 展开查看依据和不确定性, so that 我可以了解解释的来源与限制。
9. As a 患者, I want to 区分模型预测与医生确诊, so that 我不会误解结果。
10. As a 患者, I want to 围绕已发布结果追问, so that 我能获得进一步说明。
11. As a 患者, I want to 区分一般健康咨询与本次结果, so that 我不会将普通问答视为诊断结论。
12. As a 患者, I want to 自行决定是否保存获准结果, so that 正式记录反映我的授权。
13. As a 患者, I want to 重复批准时不产生重复记录, so that 我的诊断历史保持准确。
14. As a 患者, I want to 只访问自己的任务和结果, so that 我的医疗信息受到保护。
15. As a 医生, I want to 查看获授权的待复核任务、证据与草稿, so that 我能做出独立判断。
16. As a 医生, I want to 通过或不通过冻结的草稿并记录原因, so that 我的决定可追溯。
17. As a 医生, I want to 避免复核自己的任务, so that 复核保持独立。
18. As a 医生, I want to 看到 Agent 的分歧和不确定性, so that 我能重点检查问题。
19. As a 管理员, I want to 上传和管理候选参考资料, so that 证据来源可以维护。
20. As a 领域审核人员, I want to 审核资料的疾病和主题范围, so that 只有获准资料进入患者解释。
21. As a 领域审核人员, I want to 撤回失效资料, so that 后续发布和保存不能依赖旧资格。
22. As a 运维人员, I want to 查看经过权限限制的任务状态和审计, so that 我能定位故障而不过度访问患者数据。
23. As a 研究人员, I want to 比较单 Agent 与多 Agent 的解释质量, so that 我能评估协作是否带来收益。
24. As a 研究人员, I want to 回溯推理版本、证据和 Agent 结果, so that 我能重现实验并识别失败原因。
25. As a 开发人员, I want to 在进程崩溃后恢复已提交的任务, so that 任务不会静默丢失或重复发布。
26. As a 开发人员, I want to 确保旧执行者的过期结果不能提交, so that 并发重试不会覆盖有效决定。
27. As a 患者, I want to 在证据不足时得到受限状态和适当提示, so that 系统不会编造依据。
28. As a 医生, I want to 在资料撤回后阻止依赖它的后续发布或保存, so that 过期资料不会继续被当作有效依据。

## Implementation Decisions

- 多 Agent 是明确目标：Vision、Evidence、Explanation、Critic 各有独立角色约束、上下文、受限工具、结构化输出和可观察协作消息。
- Python 负责眼底图像模型推理；Java 业务服务负责身份、输入绑定、风险门控、证据资格、状态、医生复核、发布和保存授权。一次任务绑定不可变推理快照，不能把模型预测表述为确诊。
- Vision 第一版汇总现有推理和质量信息并提出再分析建议；动态预处理和重新推理只记录建议、不执行，后续独立实验。
- Evidence Agent 调用服务端控制的受控 RAG，使用经指定领域人员审核的公开资料；未删除、已启用、公开受控、审核通过、疾病及主题匹配为资格条件。普通私人知识库不自动成为临床证据。
- 证据包冻结文档版本、治理版本及片段摘要。发布、医生确认和患者批准保存前重新验证；来源失效则停止相关操作，记录受限或撤回状态。
- Explanation Agent 基于获准推理结果与冻结证据生成分层说明及引用映射；Critic 输出具体异议而不拥有发布权。程序校验与业务门禁为最终权威。
- 协调层控制消息、权限、超时和反馈预算；每个诊断任务最多自动补证一次、最多重写一次，同时设总耗时和调用上限。补证生成新的候选证据集，重新冻结，不覆盖历史版本。
- 医生只能通过或不通过冻结草稿；不通过记录原因。自动展示条件未经领域确认前默认等待医生，超时和 AI 复核不能替代医生。
- 患者进度包含后端审定的简要 Agent 工作说明；未经审核的推理文本、草稿和被门控结果不得直接展示。患者追问仅基于获准内容，不修改原诊断或授权状态。
- 患者批准保存时确认状态、正式记录和唯一回执须原子一致；重复批准回放已有结果。已发布后的来源撤回应在保存前检测并拒绝新保存。
- 资料需有最小上传、领域审核及撤回管理。外部模型调用只传经授权且完成任务必需的数据；患者身份与原图的发送范围受控。
- Graph 或领域状态机及任务调度器先做隔离 PoC 比较，业务规则和测试场景一致；Saver 的物理设计和迁移不得在协议验证前冻结。

## Testing Decisions

- 好的测试通过患者、医生、管理员可观察的公开接口验证业务行为，不断言内部调用顺序或与实现一一对应的细节。使用受控模型、时钟和外部服务替身，避免真实凭据与非确定性调用。
- 首选现有 HTTP 接口风格及独立 MockMvc 测试作为功能入口；新增诊断任务、进度、复核、资料审核、追问和授权均从其公开接口验证。复用既有用户归属、聊天历史和医生复核测试思路。
- 真实隔离 MySQL 验证事务、唯一约束、来源撤回竞争、任务恢复与过期执行者隔离；参考现有 MySQL 迁移和上传任务集成测试。Graph/调度器 PoC 单独验证跨进程恢复和协调事务。
- 覆盖文件无效、Python 超时或拒识、证据不足、Agent 输出错误、补证/重写上限、医生不可用、重复与越权操作、保存前撤回及提交前后崩溃。
- 分别标记离线替身、数据库集成、真实 Python 服务、浏览器/设备、真实模型、领域评估和临床验收；未运行不标为通过。单 Agent 基线与各 Agent 消融使用相同数据集和预先定义的指标。

## Out of Scope

- 第一版不执行动态预处理和再次图像推理，不交由 Agent 自主决定治疗或确诊。
- 不假定视觉和文本向量已对齐；多模态联合检索及量化效果属于后续研究。
- 不替换现有聊天或普通诊断入口；不自动保存正式记录；不以 Agent 投票取代业务门禁或医生。
- 不以技术演示作为临床有效性、生产上线、专利实施一致性或患者数据使用授权的证明。
