# 工单 04：旧版任务查看与显式关联重建

实施位置：`py-rewrite` / `worktree-py-rewrite`。基准提交：`ea21964d7ea87a6019a6345665d29cc383733c85`。

## 使用过程

导航中的「旧版任务」提供本人旧任务列表、详情与刷新。已保存的正式诊断记录和当前 Python 工作流分别链接到既有页面。原任务的状态、时间和版本按旧值展示，缺失时间显示「旧版未记录」。原状态不代表任务可在当前运行时继续执行。

旧任务只读接口不需要 Python `UploadInput`、当前图版本或 checkpoint：

- `GET /api/diagnosis/legacy-tasks?current=1&pageSize=20`：按原 owner 分页，最多每页 100 条。
- `GET /api/diagnosis/legacy-tasks/{sourceType}/{taskId}`：只读详情，`sourceType` 为 `workflow` 或 `upload`。
- `POST /api/diagnosis/legacy-tasks/{sourceType}/{taskId}/rebuild`：multipart 请求，必须携带新 `file`、`confirmed=true` 和 `idempotencyKey`，可提供新 `question`。

查看不会触发任务、模型、复核或正式诊断写入。匿名请求返回 401，非 owner 返回 403；医生及管理员没有隐含的跨用户查看/重建权限。无效或当前 Python 任务不能作为旧任务重建来源。

V3 `t_upload_task` 只投影标识、归属、原状态和时间；不暴露私有对象路径。旧工作流按持久化输入/执行归属区分，不能仅因当前图版本不同而被归类为 Java 任务。接口不会读取或反序列化 Java checkpoint。当前 Python 任务接口对没有 Python 输入绑定的记录返回明确的 409，引导使用旧任务视图。

## 新任务、幂等和审计

用户重新上传清晰图片、阅读重建说明并勾选确认后，创建独立的新 Python 工作流。旧输入及旧结果不自动复用，旧批准不转移。新任务从现有图片验证和 Worker 路径开始，医生复核和用户保存授权分别重新执行。

创建复用既有 `create_or_get`。新工作流、输入、START 队列任务及来源审计在成功响应前一起提交。无需变更旧 SQL、Flyway 历史或引入新的数据库迁移。新任务的初始 QUEUED 事件包含 `LEGACY_REBUILD_CONFIRMED` 原因及 `legacySource`：原任务 ID、来源类型、原创建时间/状态/版本、确认用户和确认时间。原记录、原队列任务、复核和授权不更新。新任务 HTTP/SSE 状态返回该来源关系。

专用 `legacy:` 创建键空间与普通上传入口分开；键由用户范围及调用者的幂等键绑定。相同键与相同来源/图片/新问题重试得到同一任务；更换来源或内容返回 409。MySQL 按用户的既有行串行化关联创建，避免并发重复键的锁升级死锁；同步数据库工作在线程池执行，避免阻塞事件循环。原表的不同排序规则只在查询投影统一，不改旧表定义。

浏览器保留未确认结果的请求键，网络重试及刷新后重试继续使用同一键；可以重新选择原图片。成功结果的任务链接保存在本标签页的 sessionStorage，重新打开旧任务可恢复链接。用户明确点击「再次明确确认重建」才开启新操作，清空图片及确认，随后使用新键。服务端审计与幂等不依赖浏览器存储的存活时间。
