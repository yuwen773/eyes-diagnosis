# 升级与回退手册（RC #119）

本手册供 owner 批准后执行。本轮未部署、切流或变更生产开关。任何未关闭 P0/P1 均为 NO_GO。

## 1. 四项分别验收

| 结论 | 所需证据 | 不能据此推导 |
|---|---|---|
| 旧 JAR 能启动 | 对固定摘要的可执行 JAR 实际启动，记录迁移史与健康检查 | 旧业务兼容、安全或允许切流 |
| 旧业务能运行 | 真实登录、授权、诊断、消息、上传等适用业务冒烟 | 正式复核和推理输出安全 |
| 旧安全门禁仍有效 | 正式医生复核恒拒绝、患者输出边界、跨用户拒绝、协作默认关闭的负例 | 数据恢复无损 |
| 数据可安全恢复 | 可验证备份在新库真实恢复，逐表核对停写源库与恢复库的新增/更新/删除 | 未核对的增量可以丢弃或重放 |

## 2. 按实际迁移史准入

升级前导出 `flyway_schema_history`（version、checksum、success、installed_rank），核对所有 checksum、未完成迁移和当前数据库结构。
只看最高版本号不够。禁止改已应用脚本、删 history 行、用 repair 或忽略 missing 绕过校验。

| 路径 | 升级 | 回退限制 |
|---|---|---|
| V29 且迁移史完全一致 | 只换审核过的产物 | 仅允许切换到同样包含本轮六项修复、通过四项验收的明确产物；当前尚无预先认证的旧安全产物 |
| V28 的 ui 基线 | 执行 V29 文档索引版本迁移 | 不把旧 V28 代码当作安全回退：它缺少版本准入，会接纳残留片段；优先前向修复或停服务 |
| master V17（无 V10–V14 历史） | 先备份；执行 V18–V29 | 禁止切回旧 master 对外服务。确需旧 schema，恢复备份到新库，按 §4 对账，再通过安全修补产物验收 |
| history 含本候选不存在的 V10–V14 等版本 | 不得就地升级；按 migration-matrix 重建并核验数据 | 保留原库只读；恢复到独立库，不能覆盖原库或伪造迁移史 |
| 迁移失败、checksum 不一致 | 停止切流，查明已执行 DDL 与数据状态 | MySQL DDL 不承诺事务回滚；不得假定失败等于未改变 |

V29 的 `indexVersion` 对旧文档为 NULL：旧向量不会自动获准作为证据。必须重新处理需要保留的文档并验收当前版本检索；清理失败的旧向量可保留补偿任务，但不能绕过版本门禁。

## 3. 升级前与批准后冒烟

1. 锁定候选完整 SHA、Tree SHA、JAR/静态产物摘要、配置摘要及冻结 tag；验收与待部署产物相同。
2. 暂停所有写入方（应用、队列、补偿和定时任务）。在一致性快照上备份全部应用表、迁移史、触发器和必要元数据；确认非事务表与对象存储另有一致性策略。
3. 在隔离新库真实恢复并验证，保存备份摘要、表清单、行级比较与恢复耗时。仅有 dump 文件或行数不构成恢复证明。
4. 保存原部署产物与配置，但不得未经安全验收直接启用它们。密钥仅保存在受控位置，验收文档只记配置摘要和开关值。
5. owner 批准后部署候选，检查迁移、登录、跨用户历史拒绝、工具成功/失败/TIMEOUT/CANCELLED、预算终止与刷新回放一致；上传与删除后历史和资源栏一致；RAG 只返回当前有效版本。
6. 验证正式复核写入仍被拒绝，多 Agent 前后端生产入口仍默认关闭。验证冻结 tag 未移动、生产静态文件完整且双主题响应式可用。

## 4. 恢复到新库与逐表对账

遇故障先停写，保存**故障停写时刻的源库**只读快照。备份时刻基线用于验证备份，不能代替停写源库。
将升级前备份恢复到新库，保留源库和完整备份。比较所有表的结构、主键集合及每行共有列的确定性摘要；敏感字段在受控环境比较，报告不放明文。

| 比较结果 | 处置 |
|---|---|
| 源库有、恢复库无（新增） | 列明关联依赖和对象引用；按业务语义选择迁移或经 owner 确认的数据损失；不能只比行数 |
| 相同主键、列值不同（更新） | 逐字段审查冲突、更新时间和版本；禁止用旧备份静默覆盖新状态 |
| 恢复库有、源库无（删除） | 区分物理删除、软删除、撤权与对象删除意图；不得通过恢复重新授予访问或复活已删除数据 |
| V18–V29 新表/新列 | 独立导出保留，包含任务、草稿、医生审阅、患者授权、审计和索引版本；V17 不会读取它们不等于允许丢弃 |

必须涵盖 `t_user`、`t_news`、`t_diagnosis`、`t_agent_session`、`t_agent_message`、上传任务、全部 V18–V29 数据及当前库发现的其他业务表。
用户可能注册、更新账号或被删除，诊断和消息也可能更新/删除；不能假定只存在新增消息。
同时核对数据库中的 COS 引用、物理对象、删除补偿和向量版本；仅恢复 MySQL 不会回退对象存储、Redis 或 Chroma。

记录每表新增/更新/删除数量、冲突和处置结果、未迁移记录清单、owner 接受的数据损失与时间窗口。未解决的撤权/医疗状态/跨表依赖冲突阻断切流。
新库上重新执行四项验收，并验证前后端协议兼容，owner 批准后才切换连接串/流量。原库继续只读保存，清理另行批准。

## 5. 允许的故障处置

首选前向修复；无法及时恢复时停用故障入口或停止服务。当前**没有可直接切换的已认证旧安全产物**。
将来若认证一个回退产物，必须登记完整 SHA/摘要、支持的 schema/迁移史、数据差异处置、四项验收和审批记录，不能写“上一版 JAR”作为授权。
禁止就地删表降级、覆盖原库、移动冻结 tag 或通过旧产物重新开启临床能力。

合并后冒烟仍按 §3.5–§3.6；失败时保留证据与源库，执行上述停写及前向修复/新库恢复流程。合并不授权部署。
