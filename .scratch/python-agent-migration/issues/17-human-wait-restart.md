# 17 — 验证所有人工等待流程跨重启恢复

**What to build:** 用户确认、补充信息和医生复核等待期间重启服务，相关人员仍能继续原操作，且旧审批或恢复不会重复推理或保存。

**Blocked by:** 10 — 完成最终临床复核与受限发布；11 — 实现正式诊断保存前的用户确认；12 — 补齐用户补充信息的暂停与恢复；16 — 验证并补齐任务竞争与技术失败恢复。

**Status:** ready-for-agent

**Spec:** Python Agent 迁移与眼底诊断工作流 Spec（2026-10-12）。

**Acceptance mapping:** AC-12；本票完成所列判据的相关部分，不代表提前通过整个 spec。

- [ ] 分别在待质量复核、待最终复核、待用户保存确认、待补充输入时停止并重建服务。
- [ ] 重建后通过正常用户/医生 API 继续，恢复原版本与等待原因，而非生成新任务或丢弃原决定。
- [ ] MySQL 业务记录是恢复真相，checkpoint 不覆盖工作流、审计、解释和确认状态。
- [ ] 已完成推理、复核决定和正式记录不重复产生，过期决定仍被拒绝。
- [ ] 不兼容图版本不静默恢复；失败有明确可追踪状态，不能以进程内 saver 验收。

## Verification

使用真实持久存储和应用/Worker 重建执行 HTTP 级恢复测试，记录重启前后标识、版本和业务效果。

## Constraints

只在迁移 worktree 实施，保留原 Java 源码与构建配置；Java 继续拥有三个会话端点。沿用 release 的业务 ADR、MySQL 单一业务事实来源与图决定路由。正式业务写入须用户确认，医生复核另行执行。测试模拟与真实服务结果必须区分。没有修改、删除或发布源 spec 的任务。
